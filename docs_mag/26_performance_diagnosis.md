# 26 — تشخيص الأداء: سرعة الترجمة، سرعة التنفيذ، وحجم المخرجات

**حالة الدعم:** ✅ قياسات فعلية على الإصدار v3.5 (x86_64 ELF)

> **TL;DR**
> - `magc` **أسرع بكثير في الترجمة**: 58 ms لبرنامج فيه 2000 دالة مقابل 2.5 s لـ `gcc -O2` (≈43×)،
>   وبذاكرة 6 MB مقابل 78 MB.
> - الكود المخرَج **أبطأ في الحوسبة الصرفة**: حلقة 100M تكرار استغرقت 666 ms مقابل 91 ms لـ C `-O2`
>   (≈7.3× أبطأ)، والسبب الرئيسي كثافة تعليمات المخزن/السحب على المكدس (≈40 تعليمة/تكرار مقابل 8).
> - في **كود هياكل البيانات** (جدول الـ hash) يقترب Mag من C `-O2` (1.1–1.2×) ويتفوّق على C `-O0`.
> - **تشغيل الملف التنفيذي أسرع 5×** (0.40 ms مقابل 2.1 ms) لأنه بلا libc ولا محمّل ديناميكي
>   (20 تعليمة عند الإقلاع مقابل ~146 ألف تعليمة).
> - **الحجم**: برنامج فارغ Mag أصغر (6.7 KB مقابل 15.8 KB)، لكن استيراد مكتبتين غير مستخدمتين
>   يرفعه إلى 61.6 KB لغياب حذف الكود الميت (DCE).

هذا الفصل تشخيص **عملي بالقياس** لا تنظير: كل رقم أدناه ناتج تشغيل فعلي على البيئة الموضحة،
مع مقارنة بنفس الخوارزمية مكتوبة بلغة C وترجمتها بـ `gcc -O0` و `-O2`.

## 2) سرعة الترجمة

### 2.1 الترجمة مقابل gcc

برامج اصطناعية فيها `N` دالة بسيطة `fn fN(int x) -> int { return x + N; }`، ثم `main`
يستدعي إحداها 50 مرة. النسخة C هي نفسها حرفياً.

| البرنامج | حجم المصدر | `magc` (أدنى / وسيط) | `gcc -O0` (أدنى / وسيط) | `gcc -O2` (أدنى / وسيط) | `gcc -O2 ÷ magc` |
|---|---:|---:|---:|---:|---:|
| 50 دالة | 2,083 B | 1.79 / 2.14 ms | 91 / 139 ms | 118 / 139 ms | ≈65× |
| 200 دالة | 8,284 B | 7.07 / 7.26 ms | 128 / 140 ms | 251 / 263 ms | ≈36× |
| 800 دالة | 33,484 B | 14.3 / 18.8 ms | 346 / 364 ms | 914 / 1003 ms | ≈53× |
| 2000 دالة | 85,885 B | 47.4 / 57.8 ms | 875 / 930 ms | 2430 / 2514 ms | ≈43× |

**القراءة:**
- `magc` يتدرّج تقريباً خطياً بمعدل **0.6–0.7 ms لكل KB** من المصدر الموسّع.
- جزء كبير من زمن `gcc` هو تكلفة إقلاع `gcc` ثم `cc1` ثم `as` ثم `ld` (عمليات منفصلة)،
  بينما `magc` عملية واحدة تكتب ELF مباشرة.
- أعلى استهلاك للذاكرة: `magc` **6.1 MB** (2000 دالة) و**7.4 MB** (استيراد `gui.mg`)،
  مقابل **78 MB** لـ `gcc -O2`.

### 2.2 تكلفة `use` (التوسيع النصي قبل التحليل)

المفارقة المهمة: زمن الترجمة يتبع **النص بعد توسيع الوحدات** لا حجم ملفك نفسه.

| ملف المصدر | حجم الملف | وسيط الترجمة | حجم ELF الناتج |
|---|---:|---:|---:|
| `fn main(){return 0;}` | 31 B | 1.32 ms | 6,681 B |
| `use "lib/string.mg";` | 52 B | 4.83 ms | 23,719 B |
| `use "lib/collections.mg";` | 57 B | 12.86 ms | 34,143 B |
| `use "lib/algorithm.mg";` | 55 B | 19.12 ms | 44,652 B |
| `use "lib/hashmap.mg";` | 53 B | 18.26 ms | 40,680 B |
| `algorithm` + `hashmap` معاً | 77 B | 29.69 ms | 61,613 B |
| `use "lib/json.mg";` | 53 B | 9.32 ms | 51,844 B |
| `use "lib/gui.mg";` | 49 B | 62.8–127.6 ms | 169,638 B |
| اختبار الانحدار `h01_algorithm_hashmap.mg` | 8,618 B | 17.5–40.3 ms | 99,049 B |

> ملاحظة: `algorithm.mg` يستورد `collections.mg` الذي يستورد `string.mg`؛ و`hashmap.mg`
> يستورد `string.mg`. لذلك `use "lib/algorithm.mg"` وحده يُترجم ما يقارب 3 وحدات،
> ولهذا السبب يكلف ~19 ms رغم أن ملفك لا يحتوي إلا على سطر واحد.

## 3) سرعة تنفيذ الكود المخرَج

### 3.1 النتائج

كل الأرقام وسط 7 تشغيلات، بالنانوثانية المحسوبة داخل البرنامج (`CLOCK_MONOTONIC`):

| المعيار (حجم العمل) | Mag ELF | C `-O0` | C `-O2` | `qsort` (C `-O2`) | Mag مقابل `-O2` |
|---|---:|---:|---:|---:|---:|
| حلقة حسابية 100M تكرار | **666 ms** | 302 ms | **91 ms** | — | **7.3× أبطأ** |
| `quick_sort` لـ 1M `int` | **422 ms** | 255 ms | **106 ms** | 182 ms | **4.0× أبطأ** |
| `IntIntMap`: 500K `put` | **132 ms** | 141 ms | **109 ms** | — | **1.2× أبطأ** |
| `IntIntMap`: 500K `get` | **27 ms** | 49 ms | **24 ms** | — | **1.1× أبطأ** |

**القراءة:**
- **الحوسبة الصرفة** هي نقطة الضعف: لا تحسين للحلقة، ولا توزيع سجلات، وكل عملية تمرّ
  عبر ذاكرة المكدس.
- **كود جداول الـ hash** يكاد يوازي C `-O2`، بل يتفوّق على C `-O0` في `get` بـ ~1.8×؛
  لأن العمل محدود بذاكرة الكاش أكثر من محدودية التعليمة الواحدة، وضربات `imul` في
  `hash_i64` تُنفَّذ بكفاءة.
- `quick_sort` في Mag أبطأ من `qsort` في glibc بـ ~2.3×، لكنه يظل ضمن نفس الرتبة،
  والخوارزمية نفسها (median-of-three + insertion cutoff) هي المستخدمة في الطرفين.

### 3.2 لماذا الحلقة أبطأ 7×؟ (عدّ التعليمات)

باستخدام Callgrind على نسخة 1M تكرار من الحلقة نفسها:

| التنفيذ | التعليمات المنفَّذة | تعليمة/تكرار |
|---|---:|---:|
| Mag ELF | 40,000,467 | **≈40** |
| C `-O0` | 12,153,194 | ≈12 |
| C `-O2` | 8,153,473 | ≈8 |

الأسباب التقنية (مؤكَّدة من الكود المخرَج ومن المصادر):

1. **توليد موجّه للمكدس**: التفكيك يُظهر نمط `mov value → slot(%rbp)` ثم إعادة تحميله لكل
   عملية، بدل إبقاء `s` و`i` في `rax`/`rcx`.
2. **استدعاء بالمعاملات على المكدس**: الوسائط تُدفع بـ `push` قبل `call` بدل تمريرها في
   `rdi/rsi/rdx` وفق SysV ABI، فكل استدعاء دالة يكلّف تعليمات إضافية.
3. **مُحسِّن IR شبه معدوم**: `src/ir/ir_optimizer.c:46-51` لا يحتوي إلا على 3 تمريرات:
   `fold_mov_self` و`fold_xor_zero` و`remove_nop`. لا يوجد طي ثوابت، ولا CSE، ولا DCE،
   ولا تضمين دوال (inlining)، ولا رفع ثوابت خارج الحلقة (LICM).
4. **لا متجهة SIMD ولا تقليل قوة العمليات** (strength reduction): `i * 3` تُحسب بضرب كامل
   في كل تكرار بينما يحوّلها `-O2` إلى سلسلة جمع/إزاحة.
5. **كل الأعداد `int64`** في Mag، بينما يستخدم C هنا `int64_t` أيضاً — أي أن الفرق ليس
   عرض النوع بل جودة التوليد فقط.

### 3.3 نقطة قوة: زمن الإقلاع

قياس 200 تشغيل لبرنامج لا يفعل شيء (`return 0`):

| الملف التنفيذي | الأدنى | الوسط | تعليمات عند الإقلاع (Callgrind) |
|---|---:|---:|---:|
| Mag ELF | 0.287 ms | **0.398 ms** | **20** |
| C `-O0` | 1.272 ms | 2.210 ms | 146,519 |
| C `-O2` | 1.689 ms | 2.105 ms | 146,519 |

الملف المخرَج من Mag لا يحتوي `.interp` ولا يربط glibc ولا يمرّ بمحمّل ديناميكي:
نقطة الدخول تُستدعى مباشرة بعد تهيئة المكدس. هذه ميزة تنافسية واضحة للأدوات الصغيرة
والسكربتات قصيرة العمر، ويجب الحفاظ عليها في أي تطوير مستقبلي.

## 4) أحجام الملفات المخرجة

| البرنامج | Mag ELF | C `-O0` | C `-O2` |
|---|---:|---:|---:|
| `main` فارغ | **6,681 B** | 15,776 B | 15,776 B |
| حلقة حسابية | **7,496 B** | 16,120 B | 16,064 B |
| فرز (يستورد `algorithm`) | 45,936 B | **16,416 B** | **16,192 B** |
| جدول hash (يستورد `hashmap`) | 41,935 B | **16,392 B** | **16,224 B** |
| `algorithm` + `hashmap` (بدون استدعاء أي دالة) | 61,613 B | — | — |
| `use "lib/gui.mg";` فقط | 169,638 B | — | — |

**القراءة:**
- **الخط الأساسي**: Mag أصغر بـ ~9 KB لأن ELF الخاص به مكتوب يدوياً، فيه **رأس برنامج واحد**
   ولا يوجد جدول مقاطع إطلاقاً (`readelf -S` → *There are no sections in this file*)،
   بخلاف C الذي يحمل 29 مقطعاً ومعلومات تصحيح وربط.
- **النمو**: Mag يُصدّر **كل دالة في الوحدات المستوردة حتى لو لم تُستدعَ**، فملف من 77 بايتاً
  ينتج 61 KB. C يربط الدوال المستخدمة فقط، لذا يبقى حجمه شبه ثابت (~16 KB) مهما كبر مصدره.
- لذلك: **Mag يربح في البرامج الصغيرة المستقلة، ويخسر في البرامج التي تستورد مكتبات كبيرة**.
- ملاحظة ثانوية: `magc` يطبع عند النجاح حجماً أصغر بـ 120 بايت من الحجم الحقيقي للملف
  (مثلاً: `Created 7496` ثم `Success ... 7376`)؛ الجداول أعلاه تستخدم `stat -c %s` الفعلي.

## 5) خلاصة التشخيص وأولويات التحسين

| الأولوية | التحسين المقترح | الأثر المتوقع |
|---|---|---|
| 1 | توزيع سجلات في `src/backend/x86_64/codegen.c` وإبقاء قيم الحلقة في السجلات | تقليل ~40 تعليمة/تكرار إلى ~12–15 ⇒ تقارب C `-O0` |
| 2 | تمرير وسائط الدوال بالسجلات وفق SysV ABI بدل `push` | تقليل تكلفة كل استدعاء وتحسين recursive/fib |
| 3 | توسيع `src/ir/ir_optimizer.c` بطيّ ثوابت + CSE + DCE + inlining | تقليل التعليمات وتقليص حجم ELF |
| 4 | حذف الدوال غير المستخدمة من الوحدات المستوردة (DCE على مستوى البرنامج) | `u_both` من 61 KB إلى ~10–15 KB |
| 5 | رفع ثوابت الحلقة وتقليل قوة `i*k`، ثم SIMD اختياري للمصفوفات | تحويل 7.3× إلى 2–3× في الحوسبة الكثيفة |
| 6 | الحفاظ على غياب libc/المحمّل الديناميكي | الإبقاء على ميزة الإقلاع 5× |

**الحكم الحالي:** `magc` ممتاز كـ *مترجم سريع لإنتاج ملفات صغيرة مستقلة*، وترجمة مشاريع
كاملة فيه أسرع بعشرات المرات من gcc. الكود المخرَج **ليس** بعد في مستوى C `-O2` في
الحلقات الحسابية، لكنه **جيد جداً في كود المؤشرات/الجداول** وسريع جداً في الإقلاع.
أكبر ربح واحد هو توزيع السجلات في الـ backend.

## 6) إعادة القياس

مثال أدنى لتوقيت حلقة داخل Mag (`sys_clock_gettime` تعطي ns):

```mg
extern fn sys_clock_gettime(int clk, int* tp) -> int;
extern fn print_str(string s) -> void;

fn now_ns() -> int {
    int tp[2];
    sys_clock_gettime(1, cast<int*>(tp));
    return tp[0] * 1000000000 + tp[1];
}

fn kernel(int n) -> int {
    int s = 0; int i = 0;
    while (i < n) { s = s + ((i * 3) ^ (i >> 1)); i = i + 1; }
    return s;
}

fn main() -> int {
    int t0 = now_ns();
    int s = kernel(100000000);
    print_str("ns="); print(now_ns() - t0); print_str(" sum="); print(s); print_str("\n");
    return 0;
}
```

```bash
./magc bench.mg -o bench_mag && for i in $(seq 1 7); do ./bench_mag; done
gcc -O2 bench.c -o bench_c  && for i in $(seq 1 7); do ./bench_c;  done
stat -c '%n %s bytes' bench_mag bench_c
valgrind --tool=callgrind --callgrind-out-file=/dev/null ./bench_mag 2>&1 | grep 'I  *refs'
```

> لا يمكن استخدام `perf stat` هنا لأن `perf_event_paranoid=4`؛ Callgrind بديل كافٍ لعدّ
> التعليمات (لكنه لا يقيس الزمن الحقيقي).

## 7) قياسات على بيئة التطوير الحالية (ARM64)

الأرقام في القسمين 2–6 قياسات تاريخية على x86_64 (Intel i5-8350U + gcc 13.3).
لا يوجد مشغّل x86_64 على بيئة التطوير الحالية، لذا أضفنا `tests/perf.sh` الذي
يعيد إنتاج نفس الأحمال على المضيف الحالي: ترجمة 2000 دالة وحجم ELF
بهدف x86_64، وزمن الحلقة وعدد التعليمات بهدف arm64 الأصلي.

| القياس | القيمة على هذا المضيف (arm64، بعد الإصلاحات 2.1/1.5/1.4/1.2/1.1/2.5) |
|---|---:|
| ترجمة 2000 دالة | ≈ 190 ms (وسيط 5 تشغيلات) |
| ELF فارغ / حلقة | 198 B / 198 B |
| ELF `algorithm`+`hashmap` | 69,587 B |
| ELF `gui` | 162,951 B |
| حلقة 10M تكرار | ≈ 290 ms |
| تعليمات/تكرار (Callgrind، 1M) | 83 |

> هذه الأرقام ليست بديلاً عن أرقام x86_64 أعلاه؛ الغرض منها كشف **التراجعات**
> بعد كل إصلاح. الفارق الكبير في زمن الترجمة وحجم ELF الفارغ يعكس اختلاف
> المضيف وإصدار الكاتب المباشر للـ ELF، لا تحسّناً أو تراجعاً في الخوارزمية.
>
> ملاحظة قياس: النسخة الأولى من مرحلة الفحص الدلالي (1.1) رفعت زمن ترجمة 2000
> دالة إلى ~236 ms بسبب بحث خطي عن الأسماء؛ استبداله بجدول تجزئة أعاد القياس
> إلى ~185 ms. بقية القياسات (حجم المخرجات والتعليمات) لم تتغير.
>
> إصلاح 2.5 غيّر حجم الحجز لـ `alloc<float>`/`alloc<char>` على x86_64 (من 8 بايت
> للعنصر إلى `sizeof(T)`)، ولذلك نتوقّع تغيّر بايتات ELF في الاختبارات التي تستعمل
> `alloc`؛ هذا تغيير مقصود وليس تراجعاً، ويُثبت بـ `tests/cases/s04_alloc_sizeof.mg`.
